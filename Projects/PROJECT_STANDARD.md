# AI/ML project initialization standard

This file is the source of truth for new projects created under `Projects/`.

## Trigger

When the user says they want to start, create, initialize, scaffold, or set up a
new project, apply this workflow automatically. The user does not need to mention
Python, `uv`, virtual environments, Git, tests, or editor configuration.

## First decision

Infer the smallest suitable profile from the project description:

- `minimal`: Python utilities, APIs, automation, algorithms, or unknown scope.
- `ml`: data analysis, classical ML, visualization, experimentation, or notebooks.
- `dl`: neural networks, computer vision, NLP, transformers, generative AI, or
  other PyTorch work.

Ask a question only if the choice would materially change the architecture,
language, framework, data handling, deployment target, or cost. Otherwise state
the assumption and proceed. Do not ask the user to choose package-manager details.

## Initialization procedure

1. Inspect the current directory before writing. Preserve existing files.
2. If the current directory is empty, run `ai-project . <profile>`.
3. If working from the `Projects/` parent, obtain the project name and run
   `ai-project <project-name> <profile>`.
4. If files already exist, do not run the bootstrapper blindly. Integrate its
   conventions without overwriting user work.
5. Add only dependencies justified by the requested project using `uv add` or
   `uv add --dev`. Never use global `pip install` and never borrow another
   project's `.venv`.
6. Keep secrets out of Git. Create `.env.example` with variable names only when
   the project needs credentials.
7. Put reusable implementation in `src/`, tests in `tests/`, exploratory work in
   `notebooks/`, configuration in `configs/`, and generated artifacts in
   `outputs/` or `artifacts/`.
8. Add a concise README covering purpose, setup, run, test, data, and current
   experiment status. Remove placeholder text generated by initialization.
9. For ML/DL work, make randomness, device selection, configuration, metrics,
   and checkpoint/output locations explicit. Prefer MPS on this Apple Silicon Mac
   when supported; retain CPU fallback and never assume CUDA locally.
10. Use notebooks as clients of tested code rather than the only implementation.

## Required verification

Before declaring setup complete, run as applicable:

```sh
uv sync
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run basedpyright
```

Also execute the smallest meaningful smoke test for the actual project. Report
exactly what passed, what was intentionally deferred, and the primary next
command. Do not claim success merely because files were generated.

## Git and reproducibility

- Each child of `Projects/` is its own Git repository.
- Commit `pyproject.toml`, `uv.lock`, `.python-version`, source, tests, configs,
  `.env.example`, and small metadata.
- Never commit `.venv`, secrets, datasets, model weights, checkpoints, caches, or
  generated outputs unless the user explicitly adopts an appropriate versioning
  system.
- Do not commit or publish automatically unless the user asks.
- Record dependencies through `uv`; do not maintain an independent hand-written
  `requirements.txt` unless an external platform specifically requires one.

## Changes to the standard

Project-specific requirements may override this file through a nested
`AGENTS.md`, `CLAUDE.md`, or equivalent instruction file. Update this master
standard when a convention should apply to every future project.
